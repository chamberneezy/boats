# CLAUDE.md - Lacus: Swiss Lake Boat Schedule App

## Stack and workflow
- Vite + React + TypeScript, Tailwind v4 (tokens in `src/index.css` `@theme`), `lucide-react`, `react-router`.
- Node 24 (Active LTS) is the standard runtime, switched from the older Node 20 (which reached end-of-life 2026-04). It is pinned in `.nvmrc`, required by `package.json` `engines` (`node >=24`), and used by every GitHub Actions workflow. Run `nvm use` (reads `.nvmrc`) before working locally. The requirement is real, not cosmetic: `pipeline/` runs `.ts` files directly via Node's native type stripping (needs Node >=22.18) and `react-router` needs Node >=22.22, so on older Node `npm run build:data` / `npm run test:data` fail with `Unknown file extension ".ts"`. The web app alone (`npm run dev` / `npm run build`) still runs on older Node, but standardise on 24.
- Fonts: Kanit (500/600: headings, buttons, times) and Karma (400/500: body). No others.
- Data API: `https://transport.opendata.ch/v1`.
- Do not push to GitHub, nor suggest commits, without being asked first.
- Do not suggest contacting SGV; SGV data comes from scraping their public pages (`scripts/scrape-sgv.mjs`).

## Scope
- A boat app only: results and transfers are boat-to-boat (`transportations[]=ship`). No train, bus or gondola routing; links to those may come later as information only.
- Data host: `gs://lacus-data` (public, CORS-enabled; project `lacus-app-509713`). Production reads from `https://storage.googleapis.com/lacus-data/` via `VITE_DATA_BASE_URL` (`.env.production`). Dev leaves that unset and uses the site-relative `/data` path. Users never see the bucket URL. No custom domain on the data host.
- Scheduled ingest: GitHub Actions workflow `.github/workflows/ingest-data.yml` (script `deploy/publish.sh`) builds every lake in `pipeline/lakes.ts` and rsyncs to the bucket, 3×/day. Authenticates to GCP via Workload Identity Federation, no stored key — one-time setup in `deploy/README.md`. Adding a lake is adding it to `pipeline/lakes.ts`; the next scheduled run publishes it. All twelve lakes are built this way (Constance and Maggiore added 2026-09-28, after Zug/Thun/Brienz/Biel/Neuchâtel/Murten/Lugano the same day): several operators needed care - BLS Schifffahrt AG publishes Lake Thun and Lake Brienz as two separate feed agencies (a `(ths)`/`(brs)` name suffix); "Lacs de Neuchâtel et Morat" runs Lake Neuchâtel and Lake Murten as one connected, unsplittable network (`lake-neuchatel`/`lake-murten` intentionally build the identical package); Lake Lugano's agency name ("Lago di Lugano") is a literal substring of a second, unrelated agency's name that actually serves Lake Maggiore's Swiss shore, so it's matched by `agencyId` instead of by name; Lake Maggiore is deliberately only its Swiss shore plus Cannobio (Italy) - the fuller Italian network (Stresa, Verbania, the Borromean Islands, run by Navigazione Laghi) has no open feed found anywhere, so extending it needs a bespoke scraper, not a config entry; Lake Constance needed two agencies at once (`agencyId` accepts an array) - Swiss, German and Austrian shores turned out to already be fully covered together, not the partial Swiss-only slice first assumed (see `pipeline/lakes.ts` for details on all of these). `scrape:sgv`, `scrape:zsg` and `scrape:cgn` each have their own daily workflow (`.github/workflows/scrape-{sgv,zsg,cgn}.yml`, writing committed `src/data/scraped/`, used to build the vessels package above); they and `check:zsg-traffic` share a `concurrency` group in their workflows (all four commit to `main` on close schedules, 05:00-05:30 UTC) so they queue instead of racing each other's push.
- `pipeline/` (TypeScript, plain Node): `npm run build:data` builds `pipeline/out/<lake>/timetable.<hash>.json` + `manifest.json` from the official GTFS (downloads only a newer feed, publishes only changed data; add lakes in `pipeline/lakes.ts`). The committed `public/data` copy is a safety net / local fallback, not the live source once production is pointed at the bucket. The package format is a contract for web/iOS/Android: `src/timetable/types.ts`, never change a field's meaning, bump `schemaVersion` instead. On-device search (direct + up to two changes, up to a 2-hour wait between boats (`maxWaitMinutes` in `pipeline/lakes.ts`, lowered from 16 hours on 2026-09-28 - nobody wants a "connection" that means waiting half a day at a pier), 7-day lookahead): `src/timetable/search.ts`; adapter to the app's connection shape: `toConnections.ts`. `npm run test:data` checks it against real public-API answers (`pipeline/tests/fixtures`; re-capture rarely). All times are Swiss time (`src/timetable/zurich.ts`), never the device's zone.
- Vessel/boat-name data is a second per-lake package, published to the bucket alongside the timetable (`<lake>/vessels-manifest.json` + `<lake>/vessels.<hash>.json`, same manifest+hash pattern; `src/timetable/types.ts`'s `VesselsPackage`/`VesselsManifest`, `VESSELS_SCHEMA_VERSION`). `pipeline/build-vessels.ts` (`npm run build:vessels -- --lake <id>`) builds it from `src/data/vessels.ts`'s hand-maintained catalog plus that lake's scraped allocations file, resolving each operator's own spelling of a boat's name to a catalog id **once, at publish time** - so web, iOS and Android all do the same plain `allocations[date][kurs] -> catalog[id]` lookup and never reimplement an operator's name quirks. `deploy/publish.sh` builds and rsyncs it for every lake alongside the timetable (best-effort: a lake with no scraped allocations yet, or a build failure, just publishes the timetable without it). Fetched client-side by `src/timetable/vesselsClient.ts` (same cache-then-background-refresh strategy as `client.ts`, no fallback chain - boat names are a nice-to-have, not a critical path) and consumed by `src/utils/vesselResolver.ts`, which no longer does any name-matching itself.

## Search behaviour
- Origin and Destination are autocomplete inputs over the static verified pier list in `src/piers.ts` (no `/locations` call: it also returns trains and buses). Enter picks the first match, Escape closes. With nothing typed, popular piers are shown as presets.
- Riders see short place names ("Luzern", "Bürgenstock"), never official ones. `PierOption.name` is short, `fullName` official (still searchable). Use `pierLabel()` for API station names. Short names must stay unique.
- Picking an origin (tap, Enter, or typing an exact unambiguous name) focuses the empty Destination and opens its suggestions. "Meggen" is not auto-picked because "Meggenhorn" also starts with it.
- Clearing a field (backspacing it to empty) and moving to the other field must actually clear it - the rider must never see it silently snap back to the previous pier. Leaving a field empty without picking a new one commits it as empty (placeholder shows, stays empty) rather than reverting; leaving it with unpicked leftover text also reverts (same as before). This applies to both Origin and Destination and must behave identically on touch and with a keyboard/mouse - it's a state-commit rule, not a platform-specific gesture. Bug fixed on web 2026-09-28 (`SearchForm.tsx`'s blur handler used to discard the draft unconditionally); native builds must implement this from the start, not just port the pre-fix behavior.
- The control between the fields is a swap button (ArrowLeftRight), never a plain arrow, in the form and in the collapsed summary; in the summary it reverses the trip and searches again at once.
- Date and time is one tappable line; a transparent native `datetime-local` input covers it so the phone's picker opens (separate date/time boxes render badly on iOS Safari).
- After a search the form collapses; tapping the summary reopens the origin/destination tab.
- The trip page has one CTA, "Buy ticket" (sunline-gold, `ExternalLink` icon): a link that opens the operator's shop in a new tab (first departure to last arrival, Swiss time). No booking happens in the app. **Every lake's link rule is data, not code: `src/data/shopLinks.json`** (contract `ShopLinksPackage` in `src/timetable/types.ts`), one file for all lakes and all platforms - the web bundles it, `deploy/publish.sh` publishes it to the bucket root (`shop-links-manifest.json` + `shop-links.<hash>.json`) for iOS/Android, and a push to `main` that touches it triggers that publish at once. The renderer is pure and shared by contract: `src/timetable/shopLinkRender.ts` (web; `src/shopLink.ts` only resolves pier names and calls it), ported line-for-line by iOS/Android, all three checked against `pipeline/tests/fixtures/shop-link-vectors.json` (regenerate with `pipeline/tests/capture-shop-link-vectors.ts` only when the renderer's behaviour changes on purpose, then hand the file to the native apps). So fixing or adding a link is one JSON edit, no app release. Each lake is either `kind: "search"` (a link to this exact trip: `url` + ordered `params` with placeholders `{date}` `{time}` `{from.token}` `{to.token}` `{from.name}` `{to.name}` `{from.fullName}` `{to.fullName}`, `stations` = our pier id -> the operator's own token; an unfillable placeholder gives `fallbackUrl`, or no link and a disabled button) or `kind: "page"` (the operator's ticket/timetable page, same for every trip). Status 2026-09-28: trip links for Lucerne (SGV routing shop), Zurich (ZVV timetable search; ZSG sells no tickets), Geneva (CGN, date only, no time param) and Lugano (SNL); page links for Zug, Thun, Brienz, Biel, Neuchâtel, Murten, Maggiore, Constance, each with its reason in `note`. `npm run test:data` validates the file (known placeholders only, every token keyed by a real pier of that lake, every lake has a rule). Rules: only add a `search` rule after seeing the shop accept the link (a real browser, or for a JS shop its bundle's query params plus its own API answering with real sailings); **tokens are the operator's own spelling, never derived** (SGV: `didok--fluelen--8508476` fills the field, SGV's own page's `Flueelen` opens it empty; Weggis is the shop's `Weggis+Schiffstation--8505670`, not our 8508463); a pier missing from `stations` gives no link rather than a link with an empty field, so a new pier in `src/piers.ts` needs its token checked and added. Never use a shop's per-search ids (SGV's `tickets/public-transport?journeyId=&routeId=`, ZVV's ticketshop paths, session/CSRF tokens) and never call a shop's private API from the app. Boat names, amenities and the map: never show invented data for them.

## Data and status
- Riders must never see whether data is live, cached or fallback. Source goes only to `reportDataSource()` (`src/dataSourceMonitor.ts`).
- Schedule state is a coloured dot only (`StatusBadge`), no visible text: left of the category pill on cards, next to the route on the trip page. SGV boats give no real-time data (delay/prognosis empty, no cancellation flag), so every sailing shows green "on time" unless a delay is reported (`ASSUME_ON_TIME_WITHOUT_REALTIME` in `src/connections.ts`). Delayed/cancelled need a real source (manual override or scraped notices).
- The UI calls only `searchConnections` / `loadLaterConnections` / `loadUpcomingDepartures` (`src/connections.ts`). Order: the lake's timetable package (`src/timetable/client.ts`: copy kept on the device, refreshed from the manifest in the background) -> only if it cannot answer (not loaded, date outside it, unknown pier): fresh cache (30 min) -> the public API -> stale cache -> bundled timetable (`src/data/fallbackTimetable.json`, only within its season) -> error. Normal use makes no public-API calls; keep it that way (it rate-limits with 429).
- Endpoints: `/connections?from=&to=&transportations[]=ship` (keep only `journey.category` `BAT`/`BAV`/`FAE`) and `/stationboard?id=&transportations[]=ship` (Schedules). Fields: `section.departure.platform` = pier number, `journey.number` = line (3600), `journey.name` = zero-padded Kurs (`000029`), `delay` null = no real-time. `FAE` (car ferry) is included since 2026-09-28 - foot passengers ride Zurich's Horgen-Meilen, Lucerne's Beckenried-Gersau and Constance's Friedrichshafen-Romanshorn ferries too, not just vehicles; other lakes have none.
- Vessel catalog: `VESSELS` in `src/data/vessels.ts`, a record keyed by id (`Vessel`, `AmenityTag` in `src/types.ts`). Amenity tags are supplied by the owner; `eni` and `lines` are empty until a real source exists (SGV publishes neither), never guess them. all 19 SGV boats are in it; ENI numbers are owner-supplied for 6 (Diamant and the steamers), empty for the rest.
- Boat on a trip: `resolveVesselForJourney` (`src/utils/vesselResolver.ts`) looks up the Kurs (`journey.name`) and day in that lake's published vessels package (see Scope); otherwise null. It never guesses (`lines` empty), so a day the operator hasn't published yet, or a special cruise missing from the timetable, shows no boat. The trip card shows the boat's name (never line codes like BAT 3600) with its amenity pills only when the boat is known, and shows nothing where it isn't; a known boat's type overrides the API category. The package hasn't loaded yet on first render, same as "unknown" - `TripDetails.tsx` subscribes to `subscribeVessels`/`getVesselsVersion` via `useSyncExternalStore` so it re-renders once it does.
- Pier badge ("Pier 2") only where `PierOption.has_multiple_piers` (Luzern, Weggis, from GTFS platform codes); single-pier stops show none.
- Scraped SGV data (never hand-edit): `src/data/scraped/sgv-*.json` via `npm run scrape:sgv` (about 90 s). The deployments come from the "Schiffseinsätze" search on SGV's schedule page (the form the page posts to itself), which publishes a rolling window of about two months (66 days on 2026-09-21). Each run fetches every date the page advertises plus 7 days beyond the last, and merges into `sgv-allocations.json`: fetched days replace their entry, an empty or failed day never overwrites stored data, passed days are kept 30 days. So the file grows as SGV extends its window; runs daily via `.github/workflows/scrape-sgv.yml`. If the page layout changes it exits non-zero and leaves the files untouched. `sgv-trips.json` keeps every Kurs's stops and times (routes stored once, referenced per day); it is deliberately not imported by the app (bundle size) and not published anywhere yet - it's for a future paid-app-only package, see below. **Special cruises** (evening and themed sailings, e.g. Kurs 101, 108, 110, 111, 120, 640, 1107, 1108) are exactly the Kurs present in the allocations and trips files but absent from the public timetable package (compare Kurs + first departure + last arrival); SGV gives no cruise name or description for them, only boat, day, stops and times. The published vessels package (see Scope) does include their boat assignment (it resolves every date/Kurs in the allocations file, not just ones the public timetable knows about), but nothing in the app surfaces a special-cruise trip at all today, so this is inert. The paid iOS/Android apps will show them properly (stops, times, a real trip); that publishing step is not built yet - deliberately deferred until native app work actually needs it. Product split: boat names are free tier (web + native); special cruises are paid-app-only, never shown on the web app.
- Scraped CGN data (Lake Geneva, never hand-edit): `src/data/scraped/cgn-*.json` via `npm run scrape:cgn`, daily via `.github/workflows/scrape-cgn.yml`. Source is `qr.cgn.ch`, a live "Prochains départs" board meant for QR codes posted at CGN's own piers, not linked from the normal site - found via a link on cgn.ch's traffic-info page, reverse-engineered from the app's own JavaScript (no public API CGN documents). `GET /api/qr/availableLocations` lists every pier code (43, more than the public GTFS feed's 32 - some serve charter-only cruises with no public timetable entry, the same "special cruise" situation as SGV/ZSG); `GET /api/qr/nextDepartures/<code>?datetime=<local ISO>` returns that pier's next 10 departures, each with a `vehicle.name` (verified against the public transit API to be exactly the Kurs number) - upper-cased and accent-stripped ("VILLE-DE-GENEVE" for "Ville-de-Genève"), matched to the catalog by `cgnRawForm` in `pipeline/build-vessels.ts` (publish time, not runtime - see Scope), derived from the catalog's own names rather than a hand-typed guess. Same merge/retain approach as ZSG's scraper (a fetched day only replaces its entry when it has content, kept 30 days past).
- Planned backend: Firebase/GCP (GTFS ingestion, scheduled SGV scrape, monitoring).

## Routing (`src/routes.ts` holds every URL shape)
- `/` Home, `/schedules`, `/search/lake-lucerne`, `/search/lake-lucerne?from=&to=&date=&time=` (results), `/trip/lake-lucerne?from=&to=&dep=` (one sailing). The scheme is provisional; the owner will specify the final one.
- The URL is the source of truth for search state; each trip is its own history entry; back/forward restore results without refetching.
- GitHub Pages needs `public/404.html` plus the redirect script in `index.html`; remove both once hosting rewrites all paths to `index.html`.
- Schedules: every lake (`active: true` in `src/lakes.ts` for all twelve, see above) uses real stationboard departures from its hub pier (one row per destination, `SchedulesPage.tsx`'s `HubDepartures`, branches on `lake.active`); `src/data/sampleSchedules.ts` is now unused but kept as the fallback shape for any future inactive lake.

## Screens
- Home opens with `SplashHero` at every size: full-width, full-screen owner photo (edge to edge; the copy and nav line up with the centred 1440px page container; the zoom shrinks on screens wider than ~2100px so the 2576px photo is never enlarged past its real size), transparent header floating over it (white, soft top shade, scrolls away with it), shutter doors, hero headline, rule, tag line, then a "Select your lake" button that scrolls to the lakes. Motion is ported from the Lacus Splash v2 design (`src/splash/timeline.ts`); plays once per session, skipped for reduced motion.
- Menu (`src/components/Menu.tsx`; hamburger left of the logo on desktop, left on Home on phones): X on the left, "Menu" title, app icon on the right, a placeholder (disabled) search bar, then Home, Schedules, Tickets and Account ("Coming soon"). It slides in from the left and **pushes the page aside, never covering it**: phones, the menu fills the screen and the page slides fully out; desktop, a 400px drawer and the page narrows by 400px. Phones lock page scroll. While it is open the desktop header's left group (hamburger, logo, wordmark) fades out so the logo isn't shown twice. Closes on X, Escape or navigation. State is in `src/menu.ts` (Layout in `App.tsx` reads it).
- The trip page's "Back to departures" link is desktop-only; phones use the header back arrow. On desktop the main column is wider than the map (58%, max 860px) and the trip card up to 780px.
- Lake order (`src/lakes.ts`), same on every screen size (`LakeGroups`): Lucerne, Geneva, Zurich first, then Switzerland Tourism regions: Central Switzerland (Zug), Bernese Oberland (Thun, Brienz), Jura & Three-Lakes (Neuchâtel, Biel, Murten), Eastern Switzerland (Constance), Ticino (Lugano, Maggiore). Regions are collapsed; their cards and photos render only when opened.

## Design system (Lacus; source: Lacus Mockups and Lacus Design System in Claude Design)
- Deep Lake `#16384A` (`deep-lake`): text, dark surfaces. Alpine Sky `#4A90A4` (`alpine-sky`): secondary text, eyebrows. Stone Grey `#8D9A9C` (`stone-grey`): muted text.
- Page `bg-surface-page` `#EDF3F4`; card `bg-surface-card` white with `shadow-card`; sunken `bg-surface-sunken` `#E2EBEC` for pills and placeholders; `border-hairline` dividers over card borders.
- Sunline Gold `#C99A4B` (`sunline-gold`) is the only CTA colour, white label, at most one CTA per screen; disabled `bg-cta-disabled`.
- Status dots (`bg-status-*`): on time `#3F8F5C`, delayed `#C9762E`, cancelled `#B5473F`; never a CTA colour. On time and delayed blink; cancelled does not.
- Radius 10–16px; no fully round buttons or inputs. Tabular numerals for times.
- Tone: calm, precise, sentence case, no exclamation marks or emoji. No decorative gradients (soft shadows behind text on photos are fine).
- Category pill (`CategoryPill`): neutral `bg-surface-sunken`; `BAT` (incl. electric) Ship icon "Motor vessel"; `BAV` Anchor icon "Paddle steamer"; `FAE` (car ferry, never in the vessel catalog so no known-boat override applies) Car icon "Car ferry". On phones cards show the icon only. On the trip page the boat's kind is a bare icon right after the boat's name (`CategoryIcon`), the boat's amenities are icon-only chips directly under the boat's name (`AmenityIcon`, no names), and a "Legend" (`TripLegend`) under the card names exactly the icons shown there (boat kind and that boat's amenities; nothing when no boat is known and no icon shows).
